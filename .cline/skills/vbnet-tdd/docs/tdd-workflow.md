# TDDの進め方

## まず、振る舞いを1つに絞る

機能要件を、テストできる1つの振る舞いに分ける。次の4点を決める。

- どんな入力や前提か
- どの公開APIやユースケースを呼ぶか
- 何が返るか、状態がどう変わるか
- どの境界値や異常系を確認するか

受け入れ条件が曖昧なまま実装を始めない。必要なケースを整理して、ユーザーに確認する。

## Red：先に失敗するテストを書く

最初は1件だけテストを追加する。テスト名を読めば、何を保証するテストか分かるようにする。

```text
Method_Scenario_ExpectedResult
```

例:

```text
Add_TwoNumbers_ReturnsSum
Withdraw_AmountExceedsBalance_ThrowsInsufficientFundsException
```

テストは、次の順に書く。

1. Arrange: 前提と入力を準備する
2. Act: 対象の公開APIを呼ぶ
3. Assert: 期待値や例外を確認する

テストを実行し、期待した理由で失敗することを確認する。コンパイルエラー、テスト未検出、NuGet復元エラー、環境設定エラーは、TDDのRedではない。先にテスト環境を直す。

## Green：最小限の実装で通す

失敗しているテストを通すために必要なコードだけを書く。まだ要求されていない機能、抽象化、最適化は追加しない。

Greenになったら、対象テストだけでなく、変更に関係する既存テストも実行する。

## Refactor：通る状態を保って改善する

テストが通っている状態で、次を改善する。

- 重複
- クラスやメソッドの責務
- 変数名とメソッド名
- 条件分岐の読みやすさ
- 依存関係の扱いやすさ

公開APIを変える場合は、受け入れ条件と影響範囲を先に確認する。リファクタリングの前後で同じテストを実行する。

## 次のテストケース

基本の正常系だけで終わらせず、次の順で広げる。

1. 基本的な正常系
2. 境界値
3. `Nothing`、空文字、未設定値、既定値
4. 不正な入力
5. 依存先の失敗
6. 再実行や冪等性
7. 状態遷移、キャンセル、タイムアウト、必要な並行性

## 外部依存

単体テストでは、DB、HTTP、時刻、乱数、ファイルシステムを直接使わない。既存のインターフェースや抽象化を使う。

実DBや実HTTPが必要なテストは、単体テストと統合テストを分ける。名前、カテゴリ、実行方法、必要な環境を明記する。

テスト間で静的状態、環境変数、一時ファイルを共有しない。使った場合は、テスト終了時に必ず元へ戻す。
